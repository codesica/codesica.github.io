让 Agent 发挥全部实力，到底是什么意思？

是换一个更强的模型，把推理档位拉满？是给它写一份几千字的提示词，要求它扮演架构师、产品经理和测试负责人？还是把权限全部打开，让它自己跑？

我现在更关心另一个问题：**它能不能在我不反复纠偏的情况下，把一件真正有用的事情做完。**

过去大半年，我一直在用 Codex 和不同模型做产品。东西确实做出来了，但过程并不顺畅：反复解释，反复修正，不断把偏掉的方向拉回来。能生成代码和能稳定交付，中间还有一段很长的距离。

这篇文章不讨论怎样让模型突破能力上限。我想讨论的是：对于它本来有能力处理的工作，我们有没有把它放在一个能够完成工作的环境里。

## 一、先别谈智能，看看它到底在完成什么

这个博客的搭建，就是一个很小、也很直接的例子。

第一轮，我要求尽快搭一个极简博客，让页面能够访问。Agent 找到账号下一个已有的 `blog` 仓库，在里面增加了 `gh-pages` 分支，写了一套 HTML 和 CSS，然后发布。

问题是，那个仓库原本是别人的博客项目的 fork。我需要的是自己的博客工程，不是把几个新页面放进一个无关的旧项目。页面上线了，仓库关系、技术选型和后续写作方式却不是我要的。[那一版的提交](https://github.com/codesica/blog/commit/13dabd9e6f588a1d58ffe5043f58912573af4415)仍然可以查到。

这不应该被解释成“用户没有写出一份完美的需求文档”。**Agent 在复用一个无关旧仓库之前，本来就应该核实它是否适合这个任务，而不是把“快”当成跳过判断的理由。**

后来我们重新明确方向：独立仓库，选择适合长期写作的成熟主题，用 Markdown 管理文章，提交后自动构建，并检查实际发布结果。最后才有了现在这套 [Astro、Retypeset 和 GitHub Pages 的组合](/posts/how-this-blog-works/)。主题来源和定制范围也记录在仓库的 [THEME.md](https://github.com/codesica/codesica.github.io/blob/a7b1e80c502e8f946d1fa2d129af8fb653b8e24a/THEME.md) 中。

这里最值得注意的，不是前后两版页面的差别。

而是第一轮把“能访问”当成了全部目标。它满足了一个局部条件，却没有交付那个条件背后的东西。

**执行得快，不代表目标理解得对。自动化程度再高，也可能只是在更快地把错误的事情做完。**

## 二、你是在委托工作，还是在遥控键盘

假设一个 Agent 已经具备查代码、改文件、运行测试和读取日志的能力，但你的交互方式仍然是：先让它写一个函数，再告诉它改第二个文件，接着把报错复制给它，最后提醒它去测试。

那么整个任务真正的调度者还是你。下一步做什么、需要什么信息、什么时候验证，全在你的脑子里。

它承担的是执行动作，你承担的是工程过程。

这并不是错。探索一个陌生方案时，逐步讨论很有价值；处理必须严格遵循顺序的迁移或变更时，步骤本身就是约束。但对于目标已经清楚、改动可恢复的常规工作，继续遥控每一个动作，就等于没有使用它自主寻找路径的能力。

我更愿意这样分工：**人负责什么必须成立，Agent 负责在这些条件下怎么做到。**

比如，“新增文章后，首页、文章页和订阅必须一致更新”，这是结果约束。“不要修改已有文章和主题”，这是改动边界。“先创建某个函数，再调用另一个函数”，通常只是某一种实现路径。

边界不能含糊，路径却不一定要提前写死。

反过来，只丢一句“你自己看着办”也不是委托。没有目标、授权范围和完成标准，那叫把决定权和责任一起扔出去。

## 三、规则应该补充项目事实，而不是重新发明一个 Agent

我之前一直有个疑问：编码 Agent 本来就被设计成会读代码、使用工具、检查结果，我们再给它塞一整套工作流程，会不会互相打架？

这里要先区分两件事：它具备某种能力，不等于它每一次都会正确使用；给它明确约束，也不等于必须重新教它所有软件工程常识。

我倾向于把长期指令写成项目说明，而不是角色扮演剧本。

“你是顶级工程师，要认真、严谨、专业”，没有告诉它这个项目任何新信息。“这里用哪条命令测试，哪个目录不能改，哪份文档记录当前决策，哪些接口必须向后兼容”，才是在填补它不知道的事实。

Codex 提供了 `AGENTS.md` 的分层指令机制，可以加载全局和项目范围的说明。具体加载规则应以[官方文档](https://developers.openai.com/codex/guides/agents-md)为准，不能以为随便往某个目录放一份文件，所有运行方式都会自动读取。

OpenAI 在一篇[工程实践文章](https://openai.com/index/harness-engineering/)中，也描述过从巨大指令文件改为短入口、再指向详细文档的做法。这是他们特定项目中的经验，不是某个固定行数的神奇配方。

对我来说，值得借鉴的是分工：稳定规则放在入口，细节按需查阅，临时任务留在本次任务说明里。不要把一次排错的临时措施，永久升级成所有任务都必须遵守的规定。

尤其要处理冲突：一处要求“不要修改接口”，另一处要求“顺便重构调用方式”；旧文档说用旧方案，新任务已经改变方向。继续往后追加规则并不能消除这种冲突。应该明确哪条已经失效，哪些约束仍然有效；不能擅自替用户做决定的地方，就把冲突指出来。

**指令的价值不是数量，而是减少了多少歧义。**

## 四、别只告诉它“认真检查”，让它真的看得到结果

假设一个页面有问题，Agent 能读源码，却不能启动项目、查看浏览器或读取运行日志。那它能做的主要是从代码推测运行结果。

你再要求十次“确保没有问题”，也没有增加任何新的观察手段。

同样，给了工具也不等于反馈已经接通。测试命令不存在，依赖安装失败，日志只有一句“错误”，或者浏览器检查的是另一个进程——这些都会让工具调用看起来很多，却没有真正减少不确定性。

一个有效的反馈循环应该是：提出一个可检验的判断，做一次针对性的改动，运行能区分对错的检查，再根据结果调整判断。

不是：猜一个原因，改几处代码，然后写一段“应该已经解决”。

本站的[发布工作流](https://github.com/codesica/codesica.github.io/blob/a7b1e80c502e8f946d1fa2d129af8fb653b8e24a/.github/workflows/deploy.yml)提供了一个具体例子：构建后检查生成文件和内部链接，启动静态服务器，在桌面和手机宽度下检查页面，再部署并核对线上版本。

但它也有清楚的范围：当时的浏览器检查包含首页、一篇文章、关于页导航和深浅色切换，不是每个页面、每个交互都做了完整测试。**检查覆盖到哪里，结论就只能说到哪里。**

对于一次发文任务，更直接的验收还应该包括：打开的确实是这篇新文章，标题和正文完整，首页能找到入口，RSS 里也出现了它。

这比让 Agent 在最后多写一句“已全面验证”有用。

## 五、测试通过，不等于事情做对

这里还有一个陷阱：把测试当成不会出错的裁判。

第一轮博客即使所有页面都返回正常状态，也不能证明“复用旧 fork”满足需求。检查网址连通性，无法回答仓库应该属于哪个项目。

因此我会把验收拆成两个问题：**实现有没有按设计工作，以及这个设计是不是用户真正要的。**

前者可以通过编译、测试、接口调用和浏览器检查覆盖一部分；后者需要回到目标、场景和边界。有些可以写成明确断言，有些需要人做判断。

还有一种更隐蔽的情况：实现和测试都建立在同一个错误理解上。假设需求是“未授权用户不能访问”，但 Agent 把它理解成“未登录时隐藏按钮”，那么按钮测试全部通过，也没有验证服务端授权。

这时真正需要的，是从需求独立推出反例：直接请求接口会怎样？伪造页面状态会怎样？缺少权限但已经登录又会怎样？

测试失败后，也不能允许它为了得到绿色状态，随手删除断言、跳过用例或降低标准。测试本身确实可能有错，但修改测试必须有单独的理由和证据。

**Agent 既是运动员，又参与写裁判规则时，人尤其要看清它到底证明了什么。**

## 六、自主空间不是无限权限

“别限制它”听起来很痛快，但技术权限与任务授权不是同一个东西。

一个连接可以写入多个仓库，不代表这次任务允许它修改所有仓库。它可以运行命令，也不代表可以删除生产数据。网页里出现一句要求上传文件的话，更不意味着那是用户的新指令。

我的原则是：在明确授权、能够隔离和恢复的范围内，给足完成任务所需的工具；对外发布、扩大访问范围、不可逆修改，则保留相应的边界和确认机制。已经明确授权的动作不必反复询问，超出授权的动作也不能用“提高效率”解释过去。

Codex 的[安全文档](https://learn.chatgpt.com/docs/agent-approvals-security)区分了两层控制：沙箱限制技术上能做什么，审批策略控制哪些动作需要确认。具体配置因运行环境而异，但这个区别值得保留。

最不可靠的组合，是一边在提示词里写“请小心”，一边让运行环境对所有路径、凭据和网络目标都没有限制。

**好的自主性，不是没有边界，而是不需要人在边界之内不断充当开关。**

## 七、长任务需要交接，不需要无限地说“继续”

任务一长，问题就不只是推理能力，还包括工作状态如何保存。

Anthropic 在[长时间运行 Agent 的工程实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)中，记录了进度丢失、半成品难以接续，以及过早宣布完成等问题。他们用进度记录、Git 历史和增量工作帮助后续会话恢复状态。那是特定实验的做法，但它提醒了一个实际问题：上下文能压缩，不代表工作状态就不会丢。

我不需要 Agent 把所有对话原封不动记下来。我需要它留下下一轮能够继续工作的事实。

例如，下面这样的交接记录就比一份长篇“工作总结”更有用：

```text
目标：新增文章后，正文、首页入口和订阅一致。
已完成：文章已提交；构建通过。
证据：提交编号、构建任务地址、检查报告。
未完成：正式站点尚未确认展示该提交。
已排除：不是 Markdown 解析失败。
下一步：读取线上版本信息，再检查文章地址和 RSS。
禁止：未完成线上检查前，不要声称文章已经上线。
```

这只是示例，不是本站当前的发布状态。

同样，持续运行也需要停止条件。连续尝试没有获得新证据时，应该换一种验证方法、缩小问题或报告阻塞，而不是把同一套猜测换个措辞再跑一遍。次数和成本上限应根据任务设定，没有一个适用于所有项目的万能数字。

长任务的核心不是一次跑到天荒地老，而是每一段工作都产生可以接续、可以检查、可以恢复的进展。

## 八、我会怎样真正交给它一个任务

不需要先搭一个庞大的多 Agent 系统。拿一件边界清楚的事情，把委托写明白就可以开始。

例如，给现有博客增加站内搜索，可以这样描述。下面是任务说明示例，不代表本站已经实现了搜索：

```text
目标
给现有博客增加站内搜索，读者能够按标题和正文找到已发布文章。

事实入口
先读取仓库 README、实际配置、文章结构和部署工作流。
沿用现有主题，不另建一套博客。

边界
不修改已有文章正文，不引入数据库，不接入第三方统计。
只能修改这个仓库；不要修改账号下其他项目。
本次允许在独立分支完成实现和验证，不授权发布到正式站点。

验收
中文和英文关键词都能检索；点击结果能打开对应文章。
草稿不进入索引；新增文章后索引自动更新。
无结果和空输入有合理表现；手机上能完成整个操作。
既有构建和检查通过，并说明新增测试覆盖了什么。

执行
你决定实现路径，在授权范围内自行检查、修改和验证。
遇到事实冲突、需要扩大权限或改变上述边界时再询问。
不要通过删除测试、隐藏错误或编造结果来完成任务。

交付
提供改动摘要、测试证据、已知限制和可审查的提交。
```

这段说明没有指定函数名、文件拆分或每一条命令，但目标和约束并不宽松。

搜索方案依然要由 Agent 根据项目现状判断。它还需要承担查资料、比较取舍、处理失败和证明结果的工作。

这才是我理解的“让它发挥能力”：不是我提前替它完成所有思考，再让它负责打字。

## 九、怎样判断它真的变强了

我不会用消耗了多少 token、开了多少个 Agent、生成了多少行代码来判断工作流好不好。这些可以是成本和过程记录，却不直接等于交付价值。

我更愿意记录同类任务中的四件事：通过验收的比例，人为了纠偏投入的时间，交付后发现的问题，以及任务中断后的恢复成本。

如果一份新指令让回答变长了，却没有减少返工，就不能因为它看起来专业而保留。如果增加工具后只是多了调用记录，却仍然不能发现错误，就应该检查工具返回的信息是否有效。

当然，环境也不是万能的。推理错误、知识缺口、错误的产品判断，都可能需要更合适的模型、更多资料或人的介入。把所有失败归因于 Prompt 不对，是偷懒；把所有失败归因于环境没搭好，同样是偷懒。

应该先判断失败发生在哪里，再决定改什么。

## 结语：把人从反复纠偏的位置挪开

回过头看，“让 Agent 发挥全部实力”这个说法，容易让人把注意力放在怎样再榨出一点模型能力。

但对实际工作来说，我更在意：目标有没有被理解，事实有没有被读取，权限有没有边界，行动能不能得到反馈，结果能不能被验证。

缺少这些，模型再强，也可能只是在替一个混乱的流程加速。

我希望建立的，不是一套让人完全退出的系统。而是一种更合理的分工：人把注意力放在需求、取舍、风险和最终判断上；Agent 在明确范围内，把查找、实现、验证和修正真正接起来。

**不要把 Agent 管成一双遥控的手，也不要把它放成一个不用负责的黑箱。给它清楚的目标，真实的反馈，以及必须拿证据说话的完成标准。**

让它把事情做完，比让它看起来很忙重要。
